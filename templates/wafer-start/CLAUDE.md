# wafer-start agent runbook

This file is the working guide for agents changing this template or apps scaffolded from it.

## System map

- File-based routes live in `src/routes/`.
- `src/routes/__root.tsx` owns the shared shell.
- `src/routes/app.tsx` owns the shared `/app` shell for nested product routes.
- `src/app/site.ts` owns starter-level metadata such as the app name, default description, and page-title helper.
- `src/app/auth.ts` owns the starter’s auth route names and post-auth redirect defaults.
- Route loaders fetch the data needed to render a page.
- Server functions in `src/server/functions/` are the default mutation and server-action path.
- `src/server/runtime.ts` is the service composition root. Register reusable server-side singletons there.
- Server route handlers live in route files under `src/routes/` using `server.handlers`.
- Reusable business logic belongs in `src/server/services/`.
- `src/env/server.ts` owns the typed server env contract and should be the default place to extend runtime config.
- `src/start.ts` owns request middleware such as the optional Clerk auth middleware.
- Database access belongs in `src/server/db/`.
- Shared request and response contracts live in `src/shared/`.
- `src/routeTree.gen.ts` is generated. Do not edit it by hand.

## File map

- `src/routes/`: page routes and server handlers
- `src/app/site.ts`: starter metadata and page-title helpers
- `src/env/`: typed environment parsing
- `src/server/functions/`: Start server functions
- `src/server/runtime.ts`: service composition root used by route handlers and server functions
- `src/server/services/`: server-side business logic
- `src/server/db/`: schema, bootstrap, connection, repositories
- `src/server/db/user-repository.ts`: provider-neutral app user provisioning and identity mapping
- `src/shared/schemas.ts`: shared Zod schemas and derived types
- `src/components/`: reusable UI and form components
- `tests/`: tests
- `tests/support/`: fixtures and in-memory repositories
- `scripts/`: startup, migration, and smoke wrappers

## Environment contract

- If `DATABASE_URL` exists, use it directly.
- Else if both `PG_BOOTSTRAP_URL` and `DATABASE_NAME` exist, create the app database if needed and use that.
- Else the app runs in degraded mode and `/health` returns `503`.
- Clerk auth stays off until both `VITE_CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` are present.
- Once Clerk is configured, `/sign-in` is active and `/app` becomes the default protected subtree.
- When both auth and the database are configured, the `/app` auth boundary also provisions or reuses an app-owned user record.
- Blank env values are normalized to “unset” by `src/env/server.ts`.
- Partial bootstrap config is invalid. Do not set `PG_BOOTSTRAP_URL` without `DATABASE_NAME`.
- Partial Clerk config is invalid. Do not set the Clerk publishable key without `CLERK_SECRET_KEY`, or vice versa.
- `bun run dev` may auto-apply migrations for local work; `bun run start` should not be treated as a migration step.
- If a host needs the app to bind all interfaces, set `HOST=0.0.0.0`.

## Generated files

- `src/routeTree.gen.ts` is generated by the Start build.
- Do not edit it by hand.
- If route wiring looks stale, run `bun run build`.
- Lint intentionally ignores this file.

## Naming

- Route files are noun-based and follow TanStack Start file-based routing.
- Shared schemas use names like `thingSchema`, `thingInputSchema`, and `thingResponseSchema`.
- Services use `<resource>-service.ts`.
- Repositories use `src/server/db/<resource>-repository.ts`.
- Server function modules use `src/server/functions/<resource>.ts`.
- Route-level metadata should use helpers from `src/app/site.ts` instead of hard-coded title strings.
- Avoid naming a server function module `runtime.ts`. The composition root already owns that name.

## Flow

Keep one path for reads and one path for writes:

`route loader -> server function -> service -> repository`

`form or event handler -> server function -> service -> repository`

Put shared contracts in `src/shared/` first, then consume them on both sides.

Route loader data stays the source of truth for page reads. After a successful mutation, invalidate the route so the loader refetches instead of copying loader data into local state.

## Common tasks

### Add a page

Files to touch:
- `src/routes/<page>.tsx`
- `src/server/functions/` if the page loads server data
- `tests/` if visible behavior changes

Examples:
- `src/routes/index.tsx`
- `src/routes/app.tsx`
- `src/routes/app.index.tsx`
- `src/routes/app.settings.tsx`
- `src/routes/sign-in.$.tsx`

### Add a route loader read

Files to touch:
- the owning file in `src/routes/`
- `src/server/functions/<resource>.ts`
- `src/server/runtime.ts` if the new read needs a newly composed service
- `src/server/services/<resource>-service.ts` if logic changes
- `src/server/db/<resource>-repository.ts`
- `src/shared/schemas.ts`
- `tests/`

### Add a mutation

Files to touch:
- `src/shared/schemas.ts`
- `src/server/functions/<resource>.ts`
- `src/server/runtime.ts` if the new mutation uses a newly composed service
- `src/server/services/<resource>-service.ts`
- `src/server/db/<resource>-repository.ts`
- the owning route or component in `src/routes/` or `src/components/`
- `tests/`

### Add a server route or webhook

Files to touch:
- `src/routes/<path>.tsx`
- `src/server/runtime.ts` if the handler uses a newly composed service
- `src/server/services/` if the handler needs business logic
- `src/shared/schemas.ts` if the handler accepts or returns structured data
- `tests/`

Example:
- `src/routes/health.tsx`

### Add a database-backed feature

Files to touch:
- `src/server/db/schema.ts`
- `src/server/db/<resource>-repository.ts`
- `src/server/services/<resource>-service.ts`
- `src/server/functions/<resource>.ts`
- `src/shared/schemas.ts`
- `tests/`
- `drizzle/` via `bun run db:generate`

Auth-specific note:
- Keep provider details at the auth boundary and prefer `users.id` for internal relationships. The starter’s provider link table is `auth_identities`.

## Server boundary

- Use a server function for app reads and mutations.
  Examples:
  - `src/server/functions/todos.ts`
  - `src/server/functions/runtime-info.ts`
  - `src/server/functions/auth.ts`
- Use `server.handlers` in route files only for external HTTP surfaces.
  Examples:
  - `src/routes/health.tsx`
  - future webhooks or OAuth callbacks
- When a new server function or route needs a shared service, wire it through `src/server/runtime.ts` instead of instantiating the service inline.
- Router-wide fallbacks belong in `src/components/default-not-found.tsx` and `src/components/default-catch-boundary.tsx`, then get wired through `src/router.tsx`.
- Public routes should not render raw backend exception messages or exact infrastructure identifiers.

## Worked example

### Add `notes`

Touch these files:
- `src/shared/schemas.ts`
- `src/server/db/schema.ts`
- `src/server/db/note-repository.ts`
- `src/server/services/note-service.ts`
- `src/server/functions/notes.ts`
- `src/routes/app.notes.tsx` or `src/routes/app.notes.$noteId.tsx`
- `tests/`
- `drizzle/` via `bun run db:generate`

Pattern:
- define the shared note schema first
- add the repository and service
- register the composed service in `src/server/runtime.ts`
- add a server function for reads or mutations
- add the route loader in the new route file
- if the route belongs under `/app`, hang it off `src/routes/app.tsx` with file-based naming
- add a test and generate the migration
- if the route mutates data, invalidate the route after the server function succeeds instead of keeping a second client-side copy of loader data

## Rules

- Keep route files thin.
- Keep route loaders focused on page reads.
- Keep server functions focused on server work and mutations.
- Keep repositories focused on persistence.
- Keep services focused on application behavior.
- Keep startup config reads behind `src/env/server.ts`.
- Prefer one obvious pattern over multiple equivalent ones.

## Avoid

- Do not import repository code directly into route components.
- Do not put business logic directly in route loaders or server handlers.
- Do not create a second mutation path beside server functions.
- Do not protect `/app` with a client-only check. The starter’s auth boundary belongs in `src/server/functions/auth.ts` and the parent route loader.
- Do not key internal app data directly off a provider user ID when `users.id` is available.
- Do not put server-only code in `src/shared/`.
- Do not add fresh `process.env` reads if `src/env/server.ts` can own the contract instead.
- Do not edit `src/routeTree.gen.ts` by hand.
- Do not bypass Zod validation when data crosses the client/server boundary.

## Done

- Update shared schemas if the contract changed.
- Add or update a server function if reads or mutations changed.
- Add or update a test for visible behavior.
- Generate and commit a migration if the schema changed.
- If route files changed, run `bun run build`.
- If schema files changed, run `bun run db:generate`.
- If startup, health, or runtime behavior changed, run `bun run smoke`.
- Then run `bun run check`.

## Verification

Baseline checks:

```sh
bun run lint
bun run build
bun run test
bun run check
```

Runtime and DB checks:

```sh
bun run smoke
bun run check:db
bun run db:generate
bun run db:migrate
```

`bun run check` includes the smoke test. `bun run check:db` proves the real DB-backed mutation path when DB env vars are configured. `bun run db:migrate` still needs real DB env vars.
